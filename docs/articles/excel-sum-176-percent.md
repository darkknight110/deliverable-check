# 你的 Excel 求和可能放大了 176%，而且不会报错

去年给一个客户交经营月报，第二天对方在群里问：「这个数怎么来的？」

我们复算了两遍：明细加起来 27,100.50，而报表上写的是 74,701.50。差 **2.76 倍**——多出来的部分，是表里混着的两行：一行「华东小计」，一行「合计」。

这两行在明细区里，和普通数据长得一模一样。`sum(那一列)` 把它们又加了一遍。**零报错、零警告、零 NaN**。

写代码算错会抛异常；做数据分析算错，什么都不会发生。等你发现，通常已是客户拿着报表来问「这个数怎么来的」。

## 三个来源，一个比一个安静

先说我们那张表长什么样：

```
订单号 | 区域 | 金额(元)
SO-1001 | 华东 | 12,000
SO-1002 | 华东 | 8,500.50
华东小计  |      | 20,500.50
SO-1003 | 华南 | 3,300
SO-1003 | 华南 | 3,300
合计     |      | 27,100.50
```

整列求和 = 12,000 + 8,500.5 + 20,500.5 + 3,300 + 3,300 + 27,100.5 = 74,701.5。

正确做法是明细区只放明细，小计和合计移到表外。但表不会因此报错。

第二种是数字以文本存储。`"12,000"` 和 `12000` 在 Excel 里看起来几乎一样，前者是字符串。求和时它被当成 0，或者整列被 pandas 判成 object 直接跳过，结果偏小，还不提示。带单位的更隐蔽：`"1.2 吨"` 参与不了任何计算。

第三种是两级表头和合并单元格。合并单元格在视觉上整齐，但机器读表时只有左上角有值。两级表头不显式指定 `header=[0,1]`，列名会变成 `Unnamed: 3`，后面所有口径都错位。

## 四步自查，不用工具也能做

先拿合计行当校验和：明细求和跟合计行对一遍，差超过 0.5% 就说明有一方错了。

再看列类型：数值列里有没有字符串，`df.dtypes` 一眼能看出来。

然后看空值率。某列 30% 是空，求和一定低估，先确认是「没有这个字段」还是「没录进来」。

最后看主键重复。`SO-1003` 出现两次，去重求和和逐行求和会给出两个答案。

## 一条命令体检

```bash
pipx install git+https://github.com/darkknight110/deliverable-check.git
make-dirty-sample --out /tmp/dirty.xlsx
preflight /tmp/dirty.xlsx
```

输出是真实跑出来的：

```
⛔ 明细区里有 2 行小计/合计
⛔ 6 个单元格是「带千分位的文本数字」
⛔ 「金额（元）」整列求和会放大到 2.76 倍
⛔ 「金额（元）」的合计与明细对不上（差 20,500.50）
结论：⛔ 不可交付（先修阻断项）
```

退出码 1。这一条可以直接挂进 CI 或发布门禁：数据没体检过，就发不出去。

## 两个边界，说在前面

汇总表不该按明细表体检。一张自带 `Total` 列的损益表，逐列求和无意义，工具会把这类表降级成提示，不会喊「不可交付」。

比率列不能求和。`GM %`、占比、均值，合计对不上是正常的，工具跳过。

宁可漏报一点，也不能在合法表上乱喊。一个门禁第一次误报，就会被关掉。

下次发 Excel 之前，至少做一件事：把合计行跟明细对一遍。如果这一步你也不想手动做，上面那条命令就是为它写的。
