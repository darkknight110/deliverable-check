# 你的 Excel 求和可能放大了 176%，而且不会报错

> 一张"看起来正常"的表：明细只有 27,100.50，整列求和却是 74,701.50——**放大 2.76 倍（+176%）**。
> 零报错、零警告、零 NaN。交付出去的错误答案，和正确答案长得一模一样。

这不是段子。下面这张表是真实构造的（脚本开源，可复跑），它同时踩了三个最常见的坑。

---

## 为什么"算错"没人发现

写代码算错会抛异常；做数据分析算错，**什么都不会发生**。

`sum(df["金额"])` 不会告诉你它把小计行也算进去了，也不会告诉你有一列其实是字符串。
等你发现，通常已经是客户拿着报表问："这个数怎么来的？"

---

## 三个来源，一个比一个安静

### 1. 小计/合计行混在明细里（演示里的 2.76 倍）

```
订单号 | 区域 | 金额(元)
SO-1001 | 华东 | 12,000
SO-1002 | 华东 | 8,500.50
华东小计  |      | 20,500.50     ← 明细区里的小计
SO-1003 | 华南 | 3,300
SO-1003 | 华南 | 3,300
合计     |      | 27,100.50     ← 还有一行合计
```

整列求和 = 12,000 + 8,500.5 + **20,500.5** + 3,300 + 3,300 + **27,100.5** = **74,701.5**。

正确做法是：明细区只放明细，小计/合计移到表外。**但表不会因此报错。**

### 2. 数字是文本（千分位、带单位）

`"12,000"` 和 `12000` 在 Excel 里长得几乎一样，但一个是字符串。
求和时它被当成 0，或者整列被 pandas 判成 object 直接跳过——**结果偏小，而且不提示**。

带单位的更隐蔽：`"1.2 吨"` 参与不了任何计算。

### 3. 两级表头 + 合并单元格

合并单元格在视觉上很整齐，但机器读表时只有左上角有值，其余是空。
两级表头如果不显式指定 `header=[0,1]`，列名会变成 `Unnamed: 3`，后面所有口径都错位。

---

## 四步自查（不用工具也能做）

1. **拿合计行当校验和**：明细求和 vs 合计行，差超过 0.5% 就说明有一方错。
2. **看列类型**：数值列里有没有字符串；`df.dtypes` 一眼能看出来。
3. **看空值率**：某列 30% 是空，求和一定会低估——先确认是"没有这个字段"还是"没录进来"。
4. **看主键重复**：`SO-1003` 出现两次，去重求和和逐行求和会给出两个答案。

## 想更快？一条命令体检

```bash
pipx install git+https://github.com/darkknight110/deliverable-check.git
make-dirty-sample --out /tmp/dirty.xlsx    # 造一张同样坑的表
preflight /tmp/dirty.xlsx
```

输出（真实运行结果）：

```
⛔ 明细区里有 2 行小计/合计
⛔ 6 个单元格是「带千分位的文本数字」
⛔ 「金额（元）」整列求和会放大到 2.76 倍
⛔ 「金额（元）」的合计与明细对不上（差 20,500.50）
结论：⛔ 不可交付（先修阻断项）
```

退出码是 1——可以直接挂进 CI 或发布门禁：**数据没体检过，就发不出去。**

## 两个边界，说在前面

1. **汇总表不该按明细表体检**。一张自带 `Total` 列的损益表，逐列求和无意义；
   工具会把这类表降级成提示，而不是喊"不可交付"。
2. **比率列不能求和**。`GM %`、占比、均值——合计对不上是正常的，工具会跳过。

**宁可漏报一点，也不能在合法表上乱喊**；否则这个门禁第一次误报就会被关掉。
