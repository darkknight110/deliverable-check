# 数据交付体检：先证明这个数算得对，再发出去

> **一句话**：在"看起来正常、算出来错了 176%"的脏表上，工具用 **4 条阻断** 把它拦住；
> 在真实损益表上，它给出 **0 条阻断**（并解释为什么不误报汇总表）。
> 退出码直接可接 CI：阻断即 `exit 1`。

- 工具：[`tools/audit_data.py`](../tools/audit_data.py)
- 脏表样本：[`tools/make_dirty_fixture.py`](../tools/make_dirty_fixture.py)（可现场生成，不提交二进制）

---

## 一、为什么需要它

做数据分析，**算错了什么都不会发生**：不抛异常、不报 NaN、不弹警告。
交付出去的错误数字和正确答案长得一模一样，只有下游用它做了决策才会暴露。

三类真实事故，全部做成了可机械检出的检查项：

| # | 事故 | 后果 | 谁会犯 |
|---|---|---|---|
| 1 | 小计/合计行混在明细里 | 求和**翻倍**（实测 +176%），零报错 | 所有人 |
| 2 | 数字以文本存储（千分位、带单位） | 求和得 0 或整列被静默丢弃 | 从 Excel 手工整理的表 |
| 3 | 两级表头 + 合并单元格 | 列名变 `Unnamed`，口径整体错位 | 中文报表的默认习惯 |

---

## 二、检查项

| id | 级别 | 检查什么 | 判定依据 |
|---|---|---|---|
| `total-rows-in-data` | ⛔（中间小计）/ ℹ（表尾合计） | 明细区里夹着小计/合计 | 前两列出现「合计/小计/汇总/总计」，且不在末行 |
| `double-count` | ⛔ | 整列求和会放大几倍 | 含合计行的和 ÷ 仅明细的和 > 1.01 |
| `total-mismatch` | ⛔ | 合计行不是明细的校验和 | 合计行数值与明细求和差 > 0.5% |
| `text-numbers` | ⛔ | 「12,000」这类文本数字 | 字符串匹配千分位格式 |
| `unit-in-value` | ⚠ | 「1.2 吨」写进单元格 | 值末尾带单位 |
| `merged-cells` / `multi-row-header` | ⚠ | 合并单元格、两级表头 | 合并区域 ≥3 处 / 落在表头区 |
| `duplicate-key` | ⚠ | 主键重复 | 首列（或 `--key-col`）重复值 |
| `high-empty` / `unit-missing` | ⚠ / ℹ | 空值率 >20% / 数值列表头无单位 | 逐列统计 |

**比率列自动跳过**：`GM %`、`占比`、`均值` 这类列相加没有业务意义，强行校验只会制造噪音。

**汇总表自动降级**：含 `Total` 列、且合计只在末行的表（典型的 P&L），把"求和放大"降为 ℹ —— 它本来就是汇总表，不该按明细表体检。

## 三、实测

### 3.1 脏表（`make_dirty_fixture.py`）

| 项 | 结果 |
|---|---|
| 判定 | **⛔不可交付**（4 阻断 / 7 警告 / 1 提示） |
| 求和放大 | **2.76 倍**（明细 27,100.5 → 整列 74,701.5） |
| 合计对不上 | 差 **20,500.50**（小计行被算进明细） |
| 文本数字 | 6 个 |
| 单位写进数值 | 2 个 |
| 重复主键 | 1 个（SO-1003 出现两次） |

那张表的"正确答案"是 27,100.50，而直接 `sum(整列)` 会得到 74,701.50 —— **两者都不会报错**。

### 3.2 真实表（`Coffee-Shop-Startup-Break-Even-Model.xlsx`）

| 项 | 结果 |
|---|---|
| 自动选表 | `Monthly P&L`（13 行 × 19 列），跳过封面页 |
| 判定 | ⚠ 有风险项，**0 阻断**，退出码 0 |
| 保留的警告 | 两级表头（1 条） |
| 降级为提示 | 表尾合计、各列求和放大 2.00 倍（汇总表，非缺陷） |

**这一节是反例的价值**：如果工具在真实汇总表上也喊"不可交付"，它就会被无视。宁可漏报一点，也不能在合法的汇总表上误报。

## 四、怎么用

```bash
# 人看
python3 tools/audit_data.py 交付表.xlsx --key-col 订单号

# 机器读（接 CI / devflow 门禁）
python3 tools/audit_data.py 交付表.xlsx --json
# 退出码：0 可交付；1 有阻断
```

接进 devflow 的门禁声明（`devflow.json`）：

```json
{
  "gates": {
    "data": {
      "run": "python3 tools/audit_data.py 交付/明细.xlsx",
      "negative_control": "python3 tools/audit_data.py 交付/坏样本.xlsx",
      "count_regex": "",
      "require_min_tests": 0
    }
  }
}
```

> 注意：`count_regex` 留空时，devflow 只校验退出码，不校验测试计数——对数据体检这是合理的；但**必须有负向对照**（用脏表当哨兵），否则门禁恒真。

## 五、边界（必须一起读）

1. **只覆盖 `.xlsx`**：CSV、数据库导出不在范围内（CSV 没有类型信息，问题形态不同）。
2. **只做可机械判定的检查**：口径是否合理、指标定义对不对，工具不管。
3. **「合计行当校验和」依赖表里有合计**；没有合计的表，只能查翻倍风险，查不出“算错但结构正常”。
4. **合并单元格只能提示**：工具知道它会读错，但不能替业务决定该怎么补全。
5. **比率列按表头名识别**：如果表头写成「毛利率」而值是 0.66（小数），仍会被当普通数值列——这类需要 `--key-col` 式的人为约定。
6. **不替代复算**：它是"交付前体检"，不是"业务口径评审"。
