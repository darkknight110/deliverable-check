# 中文技术方案写作基线

> **一句话**：61 份真实方案里，中位体量 **3,517 字 / 12 个二级章节 / 182 行表格**；
> 33/34 份靠表格承载信息，只有 **32%** 写了验收指标、**6%** 写了报价。
> 最容易被漏掉的两节，恰好是评审时最容易翻车的两节。

- 机器可读：[`proposal-baseline.json`](proposal-baseline.json)
- 复跑：`python3 tools/measure_proposals.py --redact --out docs/proposal-baseline.json <你的方案目录>`
  （`--redact` 把路径换成不可逆短码；公开本文件前必须加，否则会带出客户名）

---

## 一、量了什么，怎么量的

| 项 | 口径 |
|---|---|
| 语料 | `项目方案/` 下 **61 份** Markdown，**446,818** 中文字 |
| 完整方案 | 其中 34 份满足 `≥5 个二级标题 且 ≥3000 字`（排除术语表、清单、评审意见等片段） |
| 正文统计 | 剔除代码块、表格行、标题行后统计句长/段长（表格与代码不是行文，混进来会把句长拉到 80+） |
| 章节统计 | 二级标题去编号后归类；标题写法差异大，因此另按**关键词类目**跨文档统计覆盖率 |
| 重复 | 同一项目的多个版本**未去重**（V1.0 与 V1.1 同时计入），基线因此偏「历史全貌」，不是「最终稿」 |
| 脱敏 | 公开版 JSON 用 `--redact`：路径换成不可逆短码，逐文档标题省略（标题会带出项目/行业信息），只保留聚合结果 |

---

## 二、体量与结构

| 指标 | 中位数 | 说明 |
|---|---|---|
| 中文字数 | 3,517 | 完整方案；全部 61 份的中位数只有 1,366（大量片段文档） |
| 二级章节数 | 12 | 常用 7–19 |
| 标题最大层级 | 3 | 基本不写四级标题，靠表格承载细节 |
| 表格行数 | 182 | **33/34 份有表格** |
| 数字密度 | 82.5 / 千字（含表格） | 规格、金额、时限、口径都在表里 |
| 平均句长 | 51.1 字 | 偏长（见《[AI 味与返工](ai-flavor.md)》） |
| 平均段长 | 83.2 字 | — |
| 确定性词 | 1.0 / 千字 | 「一定/必然/绝对/保证」用得克制 |
| 字符画架构图 | 19/34 份 | 也正是 `md-to-office` 要替换成真图的对象 |

**结论 1：这套方案的信息密度在表里，不在散文里。**
33/34 份有表格、中位 182 行、**每千字 82.5 个数字**（含表格）——如果只读正文会觉得干瘪，其实信息都在表里。这也解释了为什么「排版」对这类文档不是审美问题：表格一乱，信息就散了。

## 三、骨架覆盖率（34 份完整方案）

| 类目 | 覆盖率 | 判断 |
|---|---|---|
| 方案 / 架构 / 设计 | 65% | 标配 |
| 风险 / 假设 / 边界 | 53% | 标配（且是质量分水岭） |
| 接口 / 集成 / 对接 | 47% | 涉系统集成时必备 |
| 实施 / 计划 / 工期 | 44% | 标配 |
| 问题 / 待确认 | 41% | 强信号：愿意把"不知道"写出来 |
| 分工 / 责任 | 41% | 标配 |
| **验收 / 指标** | **32%** | **高频缺口** |
| 背景 / 现状 / 必要性 | 21% | 常被合进"项目概述" |
| 目标 / 范围 | 21% | 常被合进"建设内容" |
| 术语 / 名词 | 15% | 多出现在大方案包（单独成册） |
| **报价 / 成本 / 预算** | **6%** | **几乎不写** |
| 运维 / 培训 / 交付 | 3% | 交付类方案才写 |

**结论 2：缺的两节，正好是最容易翻车的两节。**
验收指标缺失，意味着"做完算不算成"没有共识——评审意见里"定位错了"的根子往往在这。
报价缺失有两种解释：阶段未到（合理），或不敢定价（危险）。**基线本身不能区分，但可以提醒：如果一份方案既没有验收口径、也没有报价区间，它多半还停在"技术畅想"阶段。**

**结论 3：「问题/待确认」41% 是这套语料最值钱的习惯。**
把「我们还不知道什么」单列一节，比把假设写成事实专业得多。
但要看清一个反例：完整方案平均有 19.1 处「口径/来源」标注，评审仍然抓到 **9 处未证实前提被写成事实**——**标注次数不等于标注正确**。数量能测，正确性只能靠人核对（见《[AI 味与返工](ai-flavor.md)》的经验层）。

## 四、可执行清单（写新方案时逐条对）

**骨架（≥50% 覆盖，建议都写）**
- [ ] 方案 / 架构 / 设计（含一张分层图）
- [ ] 风险 / 假设 / 边界（含"不做什么"）
- [ ] 实施 / 计划 / 工期（里程碑 + 依赖）
- [ ] 分工 / 责任（谁做、谁验收）
- [ ] 接口 / 集成 / 对接（涉外部系统时必写）

**高频缺口（基线只有 3 成，建议补）**
- [ ] 验收 / 指标（每条目标配一个可测量的口径）
- [ ] 问题 / 待确认（把未知单列，标明"未证实"）
- [ ] 报价 / 成本区间（哪怕只给量级与计价方式）

**体量参考**
- 单份完整方案 3,000–6,000 字；超过 15,000 字应拆册（本语料里 15,000 字以上的都是合订本或评审报告）。

## 五、边界

1. **样本是自有语料**：6 个项目、同一位维护者的写法，不代表行业普遍水平。
2. **未去重版本**：V1.0 与 V1.1 同时计入，会拉低"验收/报价"覆盖率（早期版本更不完整）。
3. **只量 Markdown 源**：Word/PDF 成品的页数、图注、页眉页脚不在统计内。
4. **不评价好坏**：本基线只给结构和密度，不给"专业度"打分——那需要甲方视角的反馈数据，我们没有。
